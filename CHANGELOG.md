# Changelog

All notable changes to Cluster Optimizer will be documented in this file.

## Unreleased

- Replaced the hardcoded two-node target with a per-node-pool **minimum safe node count** derived from an actual placement simulation. The old `twoNodeEstimate` compared total requests against twice a *cluster-average* node: it returned the same target for every cluster it ever ran on, described an averaged node that exists in no heterogeneous cluster, and could not see a single scheduling constraint — a pool of three memory-optimised nodes pinned one-replica-per-host by anti-affinity got the same "2 nodes" verdict as an idle pool of ten. **New pipeline, four parts.** (1) *Evidence* — `model.Node`/`model.Pod` now carry labels, taints, pool identity, zone, schedulability, readiness, extended-resource allocatable and the kubelet pod cap; and `nodeSelector`, tolerations, required affinity/anti-affinity, topology spread, priority class and extended requests. Pool identity is keyed off provider labels (DOKS, EKS, GKE, AKS, Karpenter) with an instance-type fallback so every node belongs to exactly one pool. (2) *Usage* — a new `internal/usage` resolves observed usage from the strongest available source and stamps each reading with its fidelity: a Prometheus `quantile_over_time` subquery (`historical_p95`) or the pre-existing single metrics-server sample (`instant`). Only fidelities spanning time are `Actionable()`; a source answering for under 80% of pods is rejected as cluster-wide evidence; and asking for `prometheus` explicitly and not getting it returns *no* data rather than silently substituting a live sample, since the weaker number looks identical downstream. Pod footprints are then sized by the **more demanding** of request and p95-plus-headroom, so an under-requesting pod is modelled at its real appetite. (3) *Simulation* — `internal/binpack` runs first-fit-decreasing over a hard-predicate filter: CPU, memory, extended resources, pod cap, taints/tolerations, `nodeSelector`, required node affinity, required pod anti-affinity, `DoNotSchedule` topology spread including its `minDomains` tightening (when fewer eligible domains exist than the constraint demands, the global minimum is treated as zero exactly as the scheduler does), and the API's rule that an empty node selector term matches *no* node rather than every node. Preferred/soft terms are deliberately dropped — they change which node wins, never whether placement is possible — and every required constraint it *cannot* evaluate (PVC volume affinity, device-plugin resources, RuntimeClass overhead, `matchLabelKeys`, affinity `namespaceSelector`, order-dependent required pod affinity) returns `Indeterminate`, which is never `Feasible()`. The error direction is deliberately asymmetric: a false "does not fit" costs a missed saving, a false "fits" costs an outage. (4) *Search* — `internal/capacity` finds, per pool, the smallest N whose placement simulates, optionally requiring N−1 to still place (`CLUSTER_OPTIMIZER_SURVIVE_NODE_LOSS`, default on — this is the whole difference between a minimum and a minimum *safe*). DaemonSet footprints are charged to every retained node, 10% of allocatable is withheld so no plan depends on packing to the last megabyte, and `CLUSTER_OPTIMIZER_NODE_FLOOR` (default 2) can only raise the answer, never lower it. Three rules keep the search from ever being optimistic about capacity it does not have: an unevictable pod (bare or mirror) is excluded from the placement problem but **charged as reserved capacity on its own host**, so a pinned node never reads as empty; only nodes that are Ready and uncordoned are placement targets, since the scheduler will not place on the others — an unusable node stranding an immovable pod is still counted in the pool minimum, while one stranding nothing is reported as releasable; and the survive-one-loss gate re-simulates without the **largest** retained node rather than the smallest, so a pool held up by one big node cannot pass a gate that never asked what happens when it dies. `survive_node_loss` travels in the result so no consumer can present the number as carrying a guarantee the run never checked. Pools resolve to `fits` / `at_minimum` / `at_floor` / `indeterminate`, each naming its binding constraint. New flags/env: `--node-floor`, `--survive-node-loss`, `--usage-provider`, `--prometheus-url`, `--usage-lookback`. No new dependencies (the Prometheus HTTP API is spoken directly) and no new RBAC. The report summary key `two_node_estimate` is replaced by `capacity`; the text renderer prints it as a per-pool block and now sorts summary keys so successive runs diff cleanly. The usage resolver also rejects an unrecognised `--usage-provider` value with an explicit note instead of falling through to the weakest source in silence. 69 new tests across the three packages, nineteen of them guarding the never-be-optimistic property directly — pinned-pod capacity, node schedulability, worst-case node loss, `minDomains`, empty affinity terms, toleration effect matching, and placement determinism across 25 runs of a 40-node/400-pod snapshot.
- Redesigned the UI's optimization overview card against the new verdict. The old card had four problems, each fixed: the headline number was a constant (`2 nodes`) and therefore carried no information — it is now `current → minimum safe`, per pool; "Blocked" named no cause — each pool row and a ranked "what stands between" list now name the binding predicate in plain language and the pods it affects; red was used for states that are not faults — a correctly-sized cluster and a floor-bound one are now neutral, and an unmodelled pool is amber, with red reserved for enforcement that ran and failed; and three equal-weight rails (CPU headroom / memory headroom / observed ratio) hid which constraint actually bound — they are gone, replaced by per-pool rows that each surface only their own binding constraint. A report predating the engine renders an explicit "not evaluated" state rather than an empty card that reads as a verdict of zero. The trend series swaps the old `two_node_feasible` boolean — near-constant, so uninformative over time — for `minimum_safe_nodes` and `removable_nodes`. The remediation feed also learns the `uncordon_stale` event kind from the cordon-reaper change below.
- Fixed a live reliability bug in the nudger: a cordon it placed could be stranded forever. The nudger cordoned a node and *then* evicted its pods, writing no marker in between, so a CronJob pod that died mid-drain (OOMKill, preemption, node eviction, timeout) left a node permanently unschedulable with nothing in the cluster recording who did it or that anything was owed. Nothing ever reversed it, and each subsequent run picked a different node — quietly shrinking schedulable capacity one crash at a time. The same end state arrives without any crash: the nudger only cordons, never removes nodes, so if no autoscaler or operator removes a drained node, its cordon is not work in progress but lost capacity that nothing will notice. **Fix, in three parts.** (1) *Attribution* — `claimCordon` writes `cluster-optimizer.io/cordoned-at`, `/cordoned-by-run`, and `/prior-unschedulable` in the **same** API update that sets `Unschedulable`, so the API server applies both or neither and no cordon this tool places can be unattributable. (2) *Reaping* — at the start of every pass, before any new target is considered, `ReapStaleCordons` reverses cordons carrying our annotations that have outlived `CLUSTER_OPTIMIZER_CORDON_TTL` (new flag `--cordon-ttl`, default `30m`, `0` disables), restoring `prior-unschedulable` rather than blindly uncordoning — a cordon a human placed underneath ours survives. Cordons with no annotation are never touched; markers found on an already-uncordoned node are cleared without a write to `Unschedulable`; an unparseable timestamp is treated as stale, since giving capacity back beats stranding a node on a parse error. The node list is re-read after reaping so a node just returned to service counts toward the packing simulation. (3) *Loop prevention* — reversing a cordon stamps `cluster-optimizer.io/cordon-reaped-at`, which bars that node from being drained again for 2h while leaving it a valid destination for pods; without this the pair would oscillate, re-evicting the same workloads every cycle for no saving. The reaper sits behind the halt switch (halt means the tool touches nothing) and needs no new RBAC — `update nodes` was already granted. Each reversal writes an `uncordon_stale` remediation audit row, rendered in the UI as a distinct "returned to service" node event; a run of them is the signal that drained nodes are never actually being removed. 13 new tests cover abandoned-cordon reversal, TTL hold, foreign-cordon immunity, prior-state restoration, orphan-marker cleanup, dry-run read-only behaviour, own-run skip, TTL=0, unparseable timestamps, ownership stamping, cooldown skip, halt precedence, and reaped capacity feeding the next consolidation decision.

- Added node disk-utilization detection and an opt-in node image garbage collector that together address the "node disk filling up" alert (e.g. DigitalOcean's default 70% droplet disk warning) that the kubelet's own image GC never resolves on managed clusters, because it only triggers at 85% and is not tunable on DOKS. **Detection:** the collector now fetches each node's kubelet `stats/summary` (via a read-only `nodes/proxy` grant added to `manifests/rbac.yaml`) to record root-disk capacity/used and image-filesystem usage, plus the node's `DiskPressure` condition; the new `node-disk-utilization-high` analyzer rule flags nodes at or above 70% (medium) / 85% or under `DiskPressure` (high) and points at the pruner. Detection is read-only and runs in the existing CronJob; a node whose kubelet stats are unreachable is skipped rather than failing the run. **Active cleanup:** a new `cmd/node-image-gc` binary (shipped in the same image) runs as an opt-in DaemonSet (`manifests/daemonset-image-gc.yaml`), one pod per node, talking to the node's containerd socket over the CRI gRPC API to remove images no container references — the stale per-deploy image versions that dominate node disk. It measures disk via `statfs` on a read-only host mount and only prunes above a configurable threshold (`CLUSTER_OPTIMIZER_NODE_GC_DISK_THRESHOLD`, default 65% — below the 70% alert and the 85% kubelet GC). Mirroring every other mutation path, it is **dry-run by default** (logs what it would remove), goes live only with `CLUSTER_OPTIMIZER_NODE_GC_LIVE=true`, honours the shared halt ConfigMap, supports a `CLUSTER_OPTIMIZER_NODE_GC_MAX_REMOVALS` blast-radius cap (largest images first), and relies on the CRI's own "image in use" refusal as a second safety net. The reclaim logic is pure and unit-tested against a fake CRI (dry-run, live, threshold skip, cap, tag-vs-ID in-use matching, per-image error tolerance); the `stats/summary` parser and the disk rule have unit tests too. The DaemonSet uses a minimal namespaced ServiceAccount/Role (`cluster-optimizer-node-gc`) that can only read the halt ConfigMap; it is not privileged (runs as root only to reach the root-owned socket, drops all capabilities, read-only root filesystem). Pins `k8s.io/cri-api@v0.35.6`, `google.golang.org/grpc@v1.72.2`, and stable `google.golang.org/protobuf@v1.36.8`; only the `node-image-gc` binary links gRPC, so the optimizer/CronJob binary stays lean.

- Fixed the resource-usage analyzer (`analyzeUsage`) so the `memory-request-over-provisioned`, `memory-request-below-usage`, and `cpu-request-over-provisioned` rules compare **per-replica** request and usage instead of fleet totals. The collector sums requests and usage across every replica (`aggregatePods`), so a multi-replica workload whose per-pod request was already reasonable was flagged as over-provisioned purely because of its replica count — e.g. a Deployment with 2 replicas at 128Mi each read as a 256Mi request "less than half" of 47Mi observed. The remediation target derived from that evidence (and the patch the planner applies) is per container, so the recommendation told operators to "set memory request to 128Mi" on a container already at 128Mi: a no-op that re-fired on every run and accumulated hundreds of occurrences that could never resolve. The rule now divides by replica count (matching the per-replica math already used by `analyzeRuntimeModernization`, `analyzeHPASensitivity`, and `plan.planRequestTrim`), skips workloads with no ready replicas, and emits per-pod values in the evidence so the UI's `remediationTargetsFromEvidence` derivation stays consistent. Genuinely over-provisioned workloads still fire and now naturally stop once their per-pod request is trimmed.
